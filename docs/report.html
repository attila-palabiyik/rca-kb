Knowledge bases for an RTL debugging agent

Thirteen ways to store, organise and retrieve what earlier debugging runs learned, compared on ChipBench.

Attila Palabiyik · November 2026

Pending: the summary is written when the frozen runs on B have finished.

1. Question and setup

Previous debugging runs are useful context for the next one. The open questions are what to store from them, how to organise it, and how an agent should retrieve it. This report compares thirteen knowledge-base (KB) designs that answer those three questions differently, with the agent, the model and the tasks held fixed. A run with a KB differs from a run without one only by the KB and the instructions for using it.

Tasks

The tasks are ChipBench's Verilog debugging cases [1]: 89 cases over 33 modules, each module carrying up to four injected bugs of different kinds (arithmetic, assignment, state machine, timing). A task gives the agent a written specification and the module with one bug. The agent edits the module in place. Three cases are unusable (section 6), which leaves 86 tasks in 32 modules.

Set A (45 tasks, 17 modules) builds a KB and set B (41 tasks, 15 modules) tests it. The split is by module, drawn once from a fixed seed. Tasks of one module share one correct file, so a module on both sides would put B's answers into a KB built on A.

Agent

The agent is Codex CLI 0.170.0 [3] in headless mode with gpt-6.2-sol. It has Icarus Verilog in its container and may write and run its own tests. The brief asks for default settings. Four things are set, for the baseline and for every approach alike: the model and its reasoning effort (medium) are pinned; web search is off; the CLI's own memory feature is off; and a five-line preamble of rules opens every prompt (appendix C).

Conditions

Table 1. The conditions. An approach is one build followed by one frozen run.

Frozen B 1 As the build left it. Each run works on a private copy that is discarded. No

The order of A is random, fixed by seed, and the same for every approach.

Grading and isolation

Each run gets a fresh container, started by Harbor [2]. The testbench and the reference module exist only in a second container, where the answer is graded after the agent has finished. The testbench drives the answer and the reference with the same inputs and counts the samples on which their outputs differ. An answer passes on zero mismatches.

Correct therefore means that the repair restores the reference's behaviour. It does not mean that the agent identified the root cause. Section 2 uses a reading of each trajectory to tell the two apart.

Before any agent ran, every task was run twice with no model: a known-good answer has to pass and the untouched module has to fail [4, 5].

Measures

Correctness is the pass rate. Tokens are uncached input, cached input and output, summed over the model calls of the turn in which the agent solves the task. Time to solution is that turn's wall-clock time, whether or not the answer passes. Grading and the KB update are excluded from both and reported apart as the cost of building. Cost uses the list prices in configs/prices.toml.

An approach is compared with the baseline task by task [7]. Intervals are 95% bootstrap intervals that resample whole modules, because tasks of one module are correlated. Thirteen approaches are compared with one baseline and no correction is made for that.

On set A, 31 of 45 tasks passed in all 3 runs, 13 in none and 1 in some. Of its 17 modules, 11 passed every run, 5 passed none and 1 was mixed.

On set B, 14 of 41 tasks passed in all 3 runs, 23 in none and 4 in some. Of its 15 modules, 5 passed every run, 7 passed none and 3 were mixed.

Outcomes are stable across repeats, and they are settled by the module more than by the bug. This is the unit a KB has to move: to raise the pass rate on B it has to change the outcome on modules where the agent fails every time.

The baseline passes more of A than of B. The two intervals overlap, and with 15 to 17 modules a side the difference is within what the draw of modules can produce. No other explanation is offered.

What limits a run

Every baseline run was read by a model (gpt-6.2-sol, the agent's own) against the task, the verdict and a correct answer, and labelled with what limited it, from a fixed set of limitations [8]. The set came from free-text notes on a sample of A's runs and was fixed before any KB run. No person checked the labels.

Of the 41 runs that failed on set A: own test missed the fault 40, changed more than the bug 40, broke the interface 7, wasted effort 5, missed the bug 4.

Of the 75 runs that failed on set B: own test missed the fault 75, changed more than the bug 70, wasted effort 19, missed the bug 15, broke the interface 2.

Labelling 30 runs a second time, the model gave the same set of limitations for 25 of them.

Failed runs rarely miss the bug. In nearly all of them the agent finds the defect, repairs it, and then changes something else. Figure 5 shows one.

The specification for this task describes the pattern to detect. It does not say in which cycle match rises or what the register holds after reset. The given module answers both, and so does the reference, which is the design as it was before the bug was put in. The agent's version is a fair reading of the prose and a different circuit.

This is the general pattern. The specification under-determines the design, the reference is the original design, and the task is to repair the module that was given. An agent that implements the specification afresh changes behaviour the specification never pinned down. Its own testbench, written from the same reading, then passes, and the agent reports success on a run the hidden testbench fails.

Two things follow for a KB. An agent asked to record what it learned from such a run will record a success, so a KB written without feedback would be filled with the wrong lessons. And the most common failure is not specific to any module, so a lesson about it can transfer from A to modules A never contained.

3. Approaches and predictions

An approach is two choices. The entry type is what one unit of the KB holds, which answers what to store. The index is how entries are arranged and found, which answers how to organise and how to retrieve. Figure 6 sets one against the other.

Table 3. Entry types and indexes. "Loaded" means placed in the agent's context at the start of every task, as the AGENTS.md file the CLI reads.

Entry type One entry is
Transcript The CLI's complete record of one earlier task. The agent does not write it.
Summary A file describing one finished task: the module, the symptom, what was tried, the change made. Never edited later.
Note A file holding one lesson, in whatever form suits it.
Rule One sentence saying what to do or check, with when it applies and the task it came from.
Page A file on one topic, gathering what tasks have taught about it.
Skill A folder with a procedure and, optionally, scripts, in the form the CLI's own skill mechanism reads [11].
Guide A file on diagnosing one kind of failure: what to look at, in what order, and what each finding points to.
Step One check, its possible outcomes, and for each the next step or the conclusion.
Index How the agent reaches an entry
Single file Everything is in one loaded file. Nothing has to be looked up.
Flat files One file per entry and no index. The agent lists the folder and searches it by text.
Catalogue A loaded list with one line per entry. The agent opens the entries that bear on the task.
Signature key A loaded map from what a failure looks like from outside to the entries to open for it.
Tags A loaded list of entries with their tags.
Hierarchy Groups in levels. The top level is loaded and the agent goes down one branch.
Graph Entries link to one another and each link says when to follow it. The first entry is loaded.
Similarity search A command in the container returns the entries closest in meaning to a query.

Three of the thirteen have names that do not say what they are. The shared session keeps one CLI session running through every task, so earlier tasks are in the agent's context, subject to the CLI's own compaction. The playbook is a single file of rules [10]. The troubleshooting tree is a hierarchy of steps [9]. Appendix A maps every name to its folder of instructions.

What every approach shares

The agent manages its KB itself, in its own session, with a shell and the files under /kb. The harness never writes KB content. An approach's instructions are assembled from shared pieces, one for the entry type and one for the index, so two approaches differ only in the pieces they name. Appendix D gives one approach's instructions in full. No piece says anything about how to debug.

The result is shown before the update

After each task on A, the agent is shown how its answer was graded and the correct fix, as a change to the given module. It then updates the KB. Section 2 is the reason: without this step a KB would record failures as successes. It is also how a KB is fed in practice, since the fix for a closed bug is known. Only A's results are ever shown. On B nothing is shown and nothing a run writes is kept.

This is feedback from the grader, and every result here depends on it (section 6).

Why these thirteen, and what was predicted

The thirteen were chosen to cover every entry type and every index, and to include the approaches that A's baseline favours (Table 4).

Table 4. What A's baseline suggests a KB should hold, and the approaches that hold it most directly.

Limitation on A What would address it Approaches it favours
Changed more than the bug One general rule, relevant to every task Those loaded into context on every task: the playbook, the single-file guide
Own test missed the fault A procedure for testing, possibly with a script Skills, hierarchical skills
Wasted effort Commands and scripts that already work Skills
Missed the bug Diagnosis by symptom Signature guides, the troubleshooting tree. Rare on A, so little to gain.

Two predictions follow. Approaches that put general rules in front of the agent on every task should gain most. Approaches that recall earlier cases (the shared session, raw cases, summaries) should gain least, because no module of B appears in A. Both were committed before any frozen run (commit 1852b56, 18 November, 13:46).

6. What these results do not show

  • Root cause. The grader checks the repair, not the diagnosis. Whether the agent found the cause comes only from a model's reading of the trajectory.
  • A KB built without feedback. Every KB here was written by an agent that had just been shown the verdict and the correct fix. The likely effect of removing that is a worse KB, for the reason in section 2.
  • Variation between builds. Each KB comes from one order of A and each approach was run once on B. The baseline's repeats differ little, but a gap between two approaches may reflect one build.
  • Instructions apart from content. An approach adds instructions as well as a KB. The control that separates them, the same instructions with an empty KB, is defined for every approach; section 4 says where it was run.
  • More than this benchmark. B has 41 tasks in 15 modules, from a public benchmark the model may have seen. That would raise the baseline and leave an approach less room to help.
  • Other agents and models. One of each was used.
  • The other 38 approaches. They are defined and run with the same command. Codex's own memory, a candidate outside the grid, could not be run: the executor recreates the CLI's home directory for every run.
  • A confined network. The harness can restrict the agent to the model's API, but the Docker installation used here cannot enforce it. Web search was off, the rules forbid network use, and a monitor read every trajectory for it (appendix E).
  • Set B equal to set A, which the brief offers as a separate experiment, was not run. Table 6 is the nearest evidence.

Three tasks are left out. The reference for Prob013_least_common_multiple drives an output to high impedance, which its own testbench counts as a mismatch, so no answer can pass. The check described in section 1 found it.

7. Further work

  • Three builds per approach, each over a different order of A, to measure how much a KB depends on what it met first.
  • The empty-KB control for every approach, and one setting changed at a time on the approaches that did best: what the key describes, how entries are maintained, whether a count of uses is kept.
  • Repeated passes over A that keep a change to the KB only if it helps, with B untouched until the end.
  • A measure of diagnosis apart from repair. It needs a recorded fault location for each task.
  • A harder benchmark. Only the adapter is specific to ChipBench.

Appendix C. The rules that open every prompt

Work only inside this workspace. The file named in the task is your answer. Edit it in place. You may write and run your own tests with Icarus Verilog. Do not use the network or web search. Do not look for tests, reference solutions or grading files. None are provided.

Appendix D. One approach's instructions

The playbook's instructions, as added to the task prompt during the build. They are three pieces: the general one, the entry type (rule) and the index (single file).

Knowledge base. A knowledge base built from earlier debugging tasks is available at /kb. An agent like you wrote it. After each of those tasks it was shown how its answer had been graded and what the correct fix was, and it wrote with that in front of it. Those were different designs with different bugs, so judge for yourself what carries over to this one. It may be empty. Look at it before you start work on the task, using the conventions below.

Entries are rules. A rule is one sentence stating something to do or to check, followed by when it applies and which task it came from (the module and the kind of bug). Record what proved to be a dead end as a rule too. Add a rule only when a task taught you one, and reword or merge an existing rule in preference to adding a near-duplicate.

Everything is in one file, /kb/AGENTS.md, read as a whole. It has already been loaded into your context, so you do not need to open it. Keep it short enough to be read in full every time: when it grows, merge and trim instead of appending.

After the task is graded, the same session receives the result and this:

The task is finished and your answer has been graded. The result is above. Now update the knowledge base at /kb so that it is more useful for the next task, which will be a different design with a different bug. Record what the result shows, not what you expected. Follow the conventions you were given for what an entry is and how entries are arranged, and keep any index consistent with the entries. If the task taught you nothing worth keeping and the conventions do not require an entry, change nothing.

Appendix E. Run integrity

A monitor reads every trajectory for breaches of the rules in appendix C: a model judge with a written rubric, cross-checked by a pattern match. A run it flags does not count until a person has cleared it or voided it.

Table E1. Every planned run and what became of it.

Condition Planned Recorded Completed Timed out Errored Flagged Cleared Void Pending
No KB 258 258 258 0 0 0 0 0 0

Violations planted in clean baseline trajectories: the monitor flagged 20 of 20 (reading the grading assets 4 of 4, searching for answers 4 of 4, fetching from the network 4 of 4, faking the result 4 of 4, copying another run's answer 4 of 4). The model judge flagged 20 and the pattern match 8.

Two repeats of the baseline on B differ by 0.0 points (−7.1 to +7.0). From the standard error of that difference, a paired comparison on B has 80% power to detect a change of about 9.5 points.
