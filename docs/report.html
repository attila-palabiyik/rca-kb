Knowledge bases for an RTL debugging agent

Thirteen ways to store, organise and retrieve what earlier debugging runs learned, compared on ChipBench.

Attila Palabiyik · November 2026

Thirteen ways of keeping what a debugging agent learns were each built over 45 ChipBench tasks and then frozen and tested on 41 tasks from 15 modules the KB had never seen. With no KB, the agent (Codex CLI, gpt-6.2-sol) passed 39% of the test set. Every approach did better, by 5 to 20 points, and 7 of the 13 differences have 95% intervals that exclude zero; no approach made a single task worse. The largest gains, about 20 points each, came from the two KBs loaded whole into context on every task, a file of rules and a single-file guide, at 1.2 and 1.6 times the tokens; searching earlier transcripts and a hierarchy of diagnostic steps gained least. Each KB was built once and run once, after the agent had been shown each result during the build, and the gains are of a size this benchmark resolves only coarsely: differences under about 10 points cannot be told from noise, and a gain shared by every approach could also come from the added instructions or from the hours between the baseline and these runs.

1. Question and setup

Previous debugging runs are useful context for the next one. The open questions are what to store from them, how to organise it, and how an agent should retrieve it. This report compares thirteen knowledge-base (KB) designs that answer those three questions differently, with the agent, the model and the tasks held fixed. A run with a KB differs from a run without one only by the KB and the instructions for using it.

Tasks

The tasks are ChipBench's Verilog debugging cases [1]: 89 cases over 33 modules, each module carrying up to four injected bugs of different kinds (arithmetic, assignment, state machine, timing). A task gives the agent a written specification and the module with one bug. The agent edits the module in place. The three cases of one module are unusable (section 7), which leaves 86 tasks in 32 modules.

Set A (45 tasks, 17 modules) builds a KB and set B (41 tasks, 15 modules) tests it. The split is by module, drawn once with seed 1. Tasks of one module share one correct file, so a module on both sides would put B's answers into a KB built on A.

Agent

The agent is Codex CLI 0.170.0 [2], run headless (codex exec) with gpt-6.2-sol. It has Icarus Verilog in its container and may write and run its own tests. The brief asks for default settings. Four settings depart from the defaults, identically for the baseline and every approach: the model and its reasoning effort (medium) are pinned; web search is off; the CLI's own memory feature is off; and a five-line preamble of rules opens every prompt (appendix C).

Conditions

The order of A is random, fixed by seed, and the same for every approach. It is an order of tasks, not modules: 28 of the 45 tasks come after an earlier task of the same module.

Grading

ChipBench's testbench drives the answer and the reference module with the same inputs and counts the samples on which their outputs differ. An answer passes on zero mismatches. A pass therefore means the repair matches the reference on the testbench's inputs. It does not mean that the agent identified the root cause; section 3 labels each trajectory for, among other things, whether the agent missed the bug.

Measures

Correctness is the pass rate. Tokens are uncached input, cached input and output, summed over the model calls of the turn in which the agent solves the task. Time to solution is that turn's wall-clock time, whether or not the answer passes. Grading and the KB update are excluded from both and reported separately as the cost of building. Cost uses the list prices in configs/prices.toml, and is reported beside correctness rather than folded into it [3].

Each approach is compared with the baseline paired by task [4]. Intervals are 95% bootstrap intervals that resample whole modules, because tasks of one module are correlated. Thirteen approaches are compared with one baseline and no correction is made for that: about one of thirteen intervals would exclude zero by chance.

How small a difference can be seen follows from the baseline's own variation. Two of its repeats on B differ by 0.0 points (−7.1 to +7.0). From that, a paired difference on B has to be about 9.5 points, four tasks of 41, to be detected with 80% power. Smaller differences cannot be told from noise here.

2. How the harness works

The harness has seven components, each a package under harness/: the dataset, configuration and KB, the runner, the grader, run records, the monitor, and reporting. They share nothing but sixteen contracts, data structures each defined once in docs/spec.md (a Task, a Setup, a KB state, a Verdict, a run record and so on). A component can be replaced without touching the others: only the dataset's converter is specific to ChipBench, and only the runner's executor is specific to Harbor and Codex.

One run

A run starts in a new container, started by Harbor [5], with the task's workspace at /app and the Setup applied: the base configuration, plus the approach's overlay. The overlay is data, not code. It names the approach's instructions, its update prompt, where its KB is placed, and which KB files to link to where the CLI already looks. It may not change the model, the effort, the rules, the limits or the network, and loading fails if it tries. That is what makes the difference between a baseline run and a KB run exactly the approach.

The agent solves the task in one turn. Its answer, the files the task names and nothing else, is copied out and graded in a second container that holds the testbench and the reference. In a build run, the agent is then resumed in the same session, shown the verdict and the correct fix, and asked to update its KB. Each turn has a time limit, ten minutes to solve and five to update.

The KB as data

To the harness a KB is a directory it never reads. It needs four operations of it and nothing else: snapshot, restore, freeze and identify. A snapshot is named by a hash of its contents, so two runs that leave the KB unchanged share a name, and a chain of 45 build runs is a list of names. Every run works on a private copy of a snapshot, so runs in parallel cannot touch one another's KB. After a build run the copy becomes the next snapshot; after a frozen run it is discarded. The frozen state of every approach is committed with its runs, under runs/kb-*/kb/.

How the agent reaches the KB is the overlay's business and is kept apart from where it is stored. The approaches here use what the CLI already does: a file linked as AGENTS.md is loaded into context at the start of every task, a folder linked as the CLI's skills folder is listed by name and description, and a saved session can be resumed. For the two transcript approaches the harness copies the CLI's own session file into the KB when a run ends; that file, written by the CLI and not by the agent, is the one exception to the rule that the harness never writes KB content.

What the agent works with

The agent has a shell, the files under /app and /kb, Icarus Verilog, and one tool added for this work: kbsearch, a similarity search over a folder of files, run on a small embedding model inside the container, with no network and no tokens spent. It is in the image for every condition, and only the approach that indexes by similarity is told about it. No approach needs a server or a new interface; each is a combination of instruction pieces and the CLI's own mechanisms, which is why 51 of them could be defined and any of them run with one command.

Checking the runs

Before any agent ran, every task was run with a known-good answer, which has to pass, and with its module untouched, which has to fail [6, 7]. After every run a monitor reads the trajectory for breaches of the rules: a model judge with a written rubric, cross-checked by a pattern match. Its sensitivity was tested by planting violations in clean baseline trajectories, and it flagged all 20. A flagged run does not count until a person clears or voids it (appendix E). Every experiment records the commit of the harness that ran it and every run the hash of its Setup, and regrading every baseline answer from its record gave the same verdict for all 258.

What limits a run

Every baseline run was read by a model (gpt-6.2-sol, the agent's own) against the task, the verdict and a correct answer, and labelled with what limited it, from a fixed set of limitations [8]. The set came from free-text notes on 30 of A's runs and was fixed before any KB run. No person checked the labels.

Table 3. The limitations a run can be labelled with.

Limitation The run
Changed more than the bug addressed the defect but also changed behaviour the given module had and the reference keeps, such as output timing or reset values
Own test missed the fault passed a test of the agent's own that could not expose the fault
Wasted effort spent a clear share of its time on work that did not bear on the fix
Missed the bug did not correct the defect
Broke the interface changed names, ports or structure so that the answer no longer fits what uses it

Of the 41 runs that failed on set A: own test missed the fault 40, changed more than the bug 40, broke the interface 7, wasted effort 5, missed the bug 4.

Of the 75 runs that failed on set B: own test missed the fault 75, changed more than the bug 70, wasted effort 19, missed the bug 15, broke the interface 2.

Labelling 30 runs a second time, the model gave the same set of limitations for 25 of them.

Few failed runs missed the bug: 4 of 41 on A and 15 of 75 on B. Most repaired it and then changed something else. Figure 6 shows one.

The specification for this task describes the pattern to detect. It does not say in which cycle match rises or what the register holds after reset. The given module answers both, and so does the reference, which is the design as it was before the bug was put in. The agent's version is a fair reading of the prose and a different circuit.

The labels suggest this is the common case: 40 of 41 failed runs on A and 70 of 75 on B changed more than the bug, against 43% and 19% of runs that passed. The specification under-determines the design, the reference is the original design, and the task is to repair the module that was given. An agent that implements the specification afresh changes behaviour the specification never pinned down. Its own testbench, written from the same reading, then passes, and the agent reports success on a run the hidden testbench fails.

Two things follow for a KB. An agent asked to record what it learned from such a run will record a success, so a KB written without feedback would be filled with the wrong lessons. And the most common failure is not specific to any module, so a lesson about it can transfer from A to modules A never contained.

4. Approaches and predictions

An approach is two choices. The entry type is what one unit of the KB holds, which answers what to store. The index is how entries are arranged and found, which answers how to organise and how to retrieve. Figure 7 sets one against the other.

Table 4. Entry types and indexes. "Loaded" means placed in the agent's context at the start of every task, as the AGENTS.md file the CLI reads.

Entry type One entry is
Transcript The CLI's complete record of one earlier task. The agent does not write it.
Summary A file describing one finished task: the module, the symptom, what was tried, the change made. Never edited later.
Note A file holding one lesson, in whatever form suits it.
Rule One sentence saying what to do or check, with when it applies and the task it came from.
Page A file on one topic, gathering what tasks have taught about it.
Skill A folder with a procedure and, optionally, scripts, in the form the CLI's own skill mechanism reads [9].
Guide A file on diagnosing one kind of failure: what to look at, in what order, and what each finding points to.
Step One check, its possible outcomes, and for each the next step or the conclusion.
Index How the agent reaches an entry
Single file Everything is in one loaded file. Nothing has to be looked up.
Flat files One file per entry and no index. The agent lists the folder and searches it by text.
Catalogue A loaded list with one line per entry. The agent opens the entries that bear on the task.
Signature key A loaded map from what a failure looks like from outside to the entries to open for it.
Tags A loaded list of entries with their tags.
Hierarchy Groups in levels. The top level is loaded and the agent goes down one branch.
Graph Entries link to one another and each link says when to follow it. The first entry is loaded.
Similarity search A command in the container returns the entries closest in meaning to a query.

Three of the thirteen have names that do not say what they are. The shared session keeps one CLI session running through every task, so earlier tasks are in the agent's context, subject to the CLI's own compaction. The playbook is a single file of rules [10]. The troubleshooting tree is a hierarchy of steps [11]. Appendix A maps every name to its folder of instructions.

What every approach shares

The agent manages its KB itself, in the session that solved the task, with a shell and the files under /kb. The harness never writes KB content. An approach's instructions are assembled from shared pieces: a general one, one for the entry type and one for the index. Two approaches differ only in the pieces they name. Appendix D gives one approach's instructions in full. No piece says anything about how to debug.

The result is shown before the update

After each task on A, the agent is shown how its answer was graded and the correct fix, as a change to the given module. It then updates the KB. Section 3 is the reason: without this step a KB would record failures as successes. It is also how a KB is fed in practice, since the fix for a closed bug is known. Only A's results are ever shown. On B nothing is shown and nothing a run writes is kept.

This is feedback from the grader, and every result here depends on it (section 7). The instructions also tell the agent that earlier and later tasks are different designs. That is true on B but not of most of the build: 28 of A's 45 tasks follow a task of the same module, whose correct file they share.

Why these thirteen, and what was predicted

The thirteen were chosen to cover every entry type and every index, and to include the approaches that A's baseline favours (Table 5).

Two predictions follow. Approaches that put general rules in front of the agent on every task should gain most. Approaches that recall earlier cases (the shared session, raw cases, summaries) should gain least, because no module of B appears in A. Both were committed before any frozen run (commit 1852b56, 18 November, 13:46 US Eastern). The wording here has been edited since; the predictions have not.

5. Results

Every approach passed more of B than the agent with no KB (Figure 1, Table 6). The differences run from +4.9 to +19.5 points, and 7 of the 13 intervals exclude zero, where about one would by chance. No approach failed a task that the baseline passed in all three of its runs: every change on B is a gain. Most approaches passed at least one task in a module the baseline never passed, and the guide read on every task passed tasks in four of those seven modules (Figure 8).

The approaches cannot be ranked with confidence. The gap between two of them is about as wide as the gap between one and the baseline, and their intervals overlap almost entirely; one build and one run each is too little to separate them. What the data do show is the cost. A KB raised the tokens per run by a factor of 1.2 to 1.7, the cost by less (1.1 to 1.4), because most of the extra input is cached, and the time by about 1.4, or 2.0 where the agent ran similarity searches. The exception is the shared session, which carries every earlier task in its context: 6.7 times the tokens of a run with no KB, at nearly the same cost. Building a KB added $0.50 to $2.10 and 4 to 30 minutes to the 45 tasks of A (Table B3); the shared session, which has no update turn and keeps its context cached, cost slightly less than solving A with no KB. Since every KB run on B costs more than a run without one, no approach pays for itself in money; its return is the tasks it solves. The whole study, 1,376 runs with their KB updates and a model's reading of each, cost about $180 ($112 for the agent, $66 for the reading) in model calls.

The gains go with the limitation the baseline showed most. Against the baseline on the same tasks, the KBs removed "changed more than the bug" from 8% to 25% of B's tasks and introduced it in no more than 3.3%; the two that gained most removed it most often (Table B6).

The first prediction holds in direction: the two approaches whose KB is loaded on every task, the playbook and the single-file guide, are at the top. The second holds only in part. Raw cases, the transcripts searched by text, gained least, with the troubleshooting tree; the shared session, which recalls the same transcripts in its context, gained as much as most. The approaches that add an index the agent has to navigate (tags, a signature key, a hierarchy) gained about 10 points, less than the flat ones (12 to 17). None of these comparisons is large against the noise.

6. Discussion

What the KBs came to hold

Section 4 expected a KB read on every task to carry general rules, above all the lesson of section 3: repair the bug and keep the rest of the module. The agents wrote something else. The playbook, a single file of rules, ended the build with 32 rules, and each names one kind of design and its fix:

When debugging a shift-register detector with wildcard bits, verify each fixed bit slice and comparison literal against the pattern, as in the TopModule 011XXX110 detector where changing the registered comparison of bits [8:6] from 001 to 011 passed all 237 grading samples.

Nine of the 32 tell the agent to preserve some existing behaviour, but each does so for one kind of design ("preserve the existing registered check's sampling point" in a shift-register detector). None states the lesson in general. The other KBs that the agent wrote went the same way, from 24 tagged rules to 79 files of task summaries (Table B4): collections of cases, whatever their entry type was meant to be. The difference between approaches is then mostly how many cases the agent reads, and how.

What worked

If the gains come from what the KBs hold, and not only from their instructions (section 7), what carried from A to B is not a module's fix but a way of working on any module. The rules that tell the agent to keep a register's sampling point or a module's reset values say nothing a module of B needs to have seen; they tell the agent to repair rather than reimplement. The approaches that put such statements in front of the agent on every task, without the agent having to look for them, gained most and removed that limitation most often.

What failed

Nothing failed outright, which is itself informative: no KB misled the agent into breaking a task it could otherwise solve, and the reading of each run found a KB misleading the agent in at most 7% of an approach's runs on B. More often the KB was beside the point: the reader judged that it had no bearing on the task in 20% to 93% of runs, most for raw cases, whose transcripts are of other modules (Table B6). For a KB loaded into context the reader cannot see whether a rule was used, so these shares are lowest there by construction. Two things limited the gains. The first is that the agents did not distil. Asked to keep rules, a guide or skills, they kept cases, and the KBs grew to between 2,000 and 14,000 words (Table B4), most of it specific to modules B does not contain. The second is that the rule to work only inside the workspace led some agents not to open their KB at all, most often for the summaries (section 7).

How the choice of A affects B

Three things tie the result to this A. The first is overlap: B shares no module with A, so nothing a KB records about a module can be reused, and the gains on B must come from what generalises. On A itself, where most tasks follow an earlier task of the same module, the build's runs gained most on exactly those tasks (Figure 9), which is leakage through the shared correct file and says nothing about B.

The second is composition. With no KB the agent passes 70% of A and 39% of B, so a KB built on A learns mostly from runs that passed and from the fixes it is shown; and the kinds of failure differ, with "missed the bug" in 3% of A's runs and 12% of B's. A KB holds only what A's failures exposed. A's new modules leave little room to gain, since most of them already pass, which is why the build shows no gain on them while B, where most modules fail, shows the most.

The third is order. Each KB saw A in one order, and what it recorded from the first tasks shaped how it recorded the rest. Whether a different order gives a different KB, and a different result on B, is the first thing another run of this design should measure.

7. What these results do not show

  • Root cause. The grader checks the repair, not the diagnosis. Whether the agent found the cause comes only from a model's reading of the trajectory.
  • A KB built without feedback. Every KB here was written by an agent that had just been shown the verdict and the correct fix. Without it, a KB would likely record failed runs as successes (section 3).
  • Variation between builds. Each KB comes from one order of A and each approach was run once on B. The baseline's repeats differ little (section 1, Measures), but a gap between two approaches may reflect one build.
  • Whether the KB was read. The first rule in every prompt is to work only inside the workspace, and the KB is at /kb, outside it. Some agents declined to read their KB for that reason ("I'll keep all file access inside /app, so /kb is outside the scope of this task"). A weak result for an approach may therefore reflect a KB that was not read rather than one that did not help; the "Runs that read the KB" column of Table 6 says which.
  • Instructions and timing apart from content. An approach adds instructions as well as a KB, and its runs on B came two to five hours after the baseline's, against the same model service. A gain shared by every approach could come from either. The control that separates them, the same instructions with an empty KB run alongside, is defined for every approach but was not run, for lack of time.
  • Size and contamination. B has 41 tasks in 15 modules, from a public benchmark the model may have seen. That would raise the baseline and leave an approach less room to help.
  • Other agents and models. One of each was used.
  • The other 38 approaches. Each is defined and can be run with the same command; none was. Codex's own memory, a candidate outside the grid, could not be run: Harbor recreates the CLI's home directory for every run.
  • A confined network. The harness can restrict the agent to the model's API, but the Docker installation used here cannot enforce it. Web search was off, the rules forbid network use, and a monitor read every trajectory for it (appendix E).
  • Set B equal to set A, which the brief offers as a separate experiment, was not run. Table 7 is the nearest evidence.

Three tasks are left out: the three cases of Prob013_least_common_multiple. Its reference drives an output to high impedance, which its own testbench counts as a mismatch, so no answer can pass. The task check described in section 2 found it.

8. Further work

  • Three builds per approach, each over a different order of A, to measure how much a KB depends on what it met first.
  • The empty-KB control for every approach (defined, not run), and one setting changed at a time on the approaches that did best: what the key describes, how entries are maintained, whether a count of uses is kept.
  • Repeated passes over A that keep a change to the KB only if it helps, with B untouched until the end.
  • A measure of diagnosis apart from repair. It needs a recorded fault location for each task.
  • A harder benchmark. Only the converter from ChipBench's format is specific to ChipBench.

Work only inside this workspace.
The file named in the task is your answer. Edit it in place.

Do not use the network or web search.

Appendix D. One approach's instructions

The playbook's instructions, as added to the task prompt during the build. They are three pieces: the general one, the entry type (rule) and the index (single file).

Knowledge base. A knowledge base built from earlier debugging tasks is available at /kb. An agent like you wrote it. After each of those tasks it was shown how its answer had been graded and what the correct fix was, and it wrote with that in front of it. Those were different designs with different bugs, so judge for yourself what carries over to this one. It may be empty. Look at it before you start work on the task, using the conventions below.

Entries are rules. A rule is one sentence stating something to do or to check, followed by when it applies and which task it came from (the module and the kind of bug). Record what proved to be a dead end as a rule too. Add a rule only when a task taught you one, and reword or merge an existing rule in preference to adding a near-duplicate.

Everything is in one file, /kb/AGENTS.md, read as a whole. It has already been loaded into your context, so you do not need to open it. Keep it short enough to be read in full every time: when it grows, merge and trim instead of appending.

After the task is graded, the same session receives the result and this:

The task is finished and your answer has been graded. The result is above. Now update the knowledge base at /kb so that it is more useful for the next task, which will be a different design with a different bug. Record what the result shows, not what you expected. Follow the conventions you were given for what an entry is and how entries are arranged, and keep any index consistent with the entries. If the task taught you nothing worth keeping and the conventions do not require an entry, change nothing.

Appendix E. Run integrity

A monitor reads every trajectory for breaches of the rules in appendix C: a model judge with a written rubric, cross-checked by a pattern match. A run it flags does not count until a person has cleared it or voided it.

Every flag raised on a KB run was one of two kinds, and each was cleared after review, with a note in the experiment's reviews.json. In the first, the agent read its KB at /kb, or declined to, and the judge counted the path as outside the workspace. In the second, a build task's KB already held the fix because an earlier task of the same module had been shown it (section 4). One flag of the second kind was labelled as targeting the grader: the agent kept a traffic-light module's reset timing against the written specification because its KB recorded three earlier fixes of the same module that kept it. The runs whose evidence did not explain itself were read in full; none touched the tests, the reference or the network.
