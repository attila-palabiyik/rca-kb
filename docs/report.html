Knowledge bases for an RTL debugging agent

Attila Palabiyik · November 2026

Summary

To be written when the results are in.

1. Setup

The question is which way of storing and retrieving what earlier debugging runs learned helps a later run most. The thing under test is a knowledge base (KB) approach. The agent, the model and everything else are held fixed, and a run with a KB differs from a run without one by exactly the approach's own configuration.

Agent. Codex CLI 0.170.0 [3], headless, with gpt-6.2-sol at medium reasoning effort. Web search is off and the CLI's own memory is off. Every prompt opens with the same five lines of rules. Everything else is the CLI's default.

Benchmark. ChipBench's Verilog debugging cases [1]. Each gives a written specification and a module with one injected bug. The agent edits the module in place. A hidden testbench then compares it with a reference on every sample, and the answer passes on zero mismatches. There are 33 modules, each with up to four different bugs.

Split. Set A builds a KB and set B tests it. The split is by module, so no module has tasks on both sides. Tasks of one module share one correct file, and a module on both sides would put B's answers into a KB built on A.

Conditions. Table 1 lists them.

Table 1. The three conditions. An approach is run as a build followed by a frozen run.

Condition Tasks KB
Baseline A and B None
Build A, one task after another Starts empty. Each task is solved with the KB as it stands; the agent then updates it.
Frozen B The KB as the build left it. Nothing a run writes is kept.

Isolation and grading. Every run gets a fresh container, started by Harbor [2]. The testbench and the reference exist only in a second container, where the answer is graded after the agent has finished. Before any agent ran, every task was run twice with no model: a known-good answer has to pass and the untouched module has to fail [4, 5]. Three tasks failed that check and are left out (section 6).

Measures. Correctness is the testbench's verdict. Tokens and time are the agent's own, for the turn in which it solves the task, and are reported beside correctness [6]. An approach is compared with the baseline task by task. Intervals come from resampling whole modules, since tasks of one module stand or fall together [7].

2. What the baseline shows

Table 2. The baseline: the agent with no KB, three repeats per task. pass@3 counts a task as solved if any repeat passes, pass^3 only if all three do.

Set Tasks Runs Pass rate (95% interval) pass@3 pass^3 Tokens per run Cost per run Time to solution
A 45 135 69.6% (45.7 to 90.8) 71.1% 68.9% 70k $0.061 31 s
B 41 123 39.0% (19.0 to 62.5) 43.9% 34.1% 75k $0.066 37 s

On set A, 68.9% of tasks pass in every repeat, 28.9% in none, and 2.2% in some but not all.

On set B, 34.1% of tasks pass in every repeat, 56.1% in none, and 9.8% in some but not all.

Three things stand out.

B is harder than A. The split was drawn once, by module, from a fixed seed, and was not adjusted afterwards.

The outcome is settled by the task, not by chance. Few tasks pass in some repeats and fail in others. Whole modules pass or fail together, whichever bug was injected.

Most failures are not a missed bug. Every baseline run was read against the task, the verdict and a correct answer, and what limited it was recorded under a fixed set of categories [8]. The categories came from free-text notes on a sample of A's runs and were fixed before any KB run. Figure 1 gives their shares.

The limitations are a model's reading of every run, and a run can show several. Read twice, the reader named the same set of limitations for 83.3% of 30 runs.

In the commonest failure the agent finds the defect and then keeps going. It rewrites the module to match the written specification, and in doing so moves an output by a clock cycle or changes a reset value that the original code had and the reference keeps. One sequence detector had its shift register filling from the wrong end. Swapping two operands was the whole fix. The agent made that swap, and also moved the comparison so that the output rose a cycle earlier.

The second commonest goes with it. The agent writes its own testbench, often an exhaustive one, and the testbench passes, because it encodes the same reading of the specification as the rewrite. From where the agent stands, the run succeeded.

This matters for what a KB can do. An agent asked to record what it learned from such a run will record a success.

3. The approaches

An approach is two choices: what one entry in the KB is, and how entries are found. Each combination that makes sense is an approach. Table 3 lays them out, with the thirteen that were run in bold.

Table 3. The approaches, by entry (rows) and index (columns). Bold: run. A dot: makes sense, not run. Empty: does not make sense.

Entry Single file Flat files Catalogue Signature key Tags Hierarchy Graph Similarity search

Note · Notes · · · · · Notes by similarity

Step · · Troubleshooting tree ·

An empty cell is a combination that means nothing: a rule is too small to be a file of its own, and a step means nothing without the steps it leads to.

The rows run from records of what happened (transcripts, summaries), through statements of what is true (notes, rules, pages), to instructions for what to do (skills, guides, steps). The columns run from no structure at all to the most. A single file is read whole on every task. A catalogue is one line per entry. A signature key maps what a failure looks like to the entries for it. Some cells take their form from published designs: the playbook from [10], skills from [11], and the troubleshooting tree from [9].

What is the same in all of them. The agent manages its KB itself, in its own session, with the tools it already has. The harness never writes KB content. An approach's instructions are assembled from shared pieces, one for the entry type and one for the index, so two approaches differ only in the pieces they name. No piece says anything about how to debug.

The result is shown before the update. After each task on A the agent is told how its answer was graded and shown the correct fix, as a change to the original module. It then updates the KB. Section 2 is the reason: without this, most of what the KB recorded would be failures written down as successes. It is also how a KB is fed in practice, since once a bug is closed its fix is known. Only A's results are ever shown, and B's modules do not appear in A.

Why these thirteen. They were chosen for two things. Together they cover every kind of entry and every kind of index. And they include the approaches that A's baseline points to (Table 4).

Table 4. What A's baseline suggests a KB should hold, and the approaches that hold it most directly.

Limitation on A What would address it Approaches it favours
Changed more than the bug One general rule, relevant to every task Those the agent sees without looking: the playbook, the single-file guide
Own test could not expose the fault A procedure, possibly with a script Skills, hierarchical skills
Wasted a share of the run Commands and scripts that already work Skills
Missed the bug Diagnosis by symptom Signature guides, the troubleshooting tree. Rare on A, so little to gain.

On this reading the approaches that put a general rule in front of the agent on every task should gain most. Those that recall earlier cases (the shared session, raw cases, summaries) should gain least, because none of B's modules appears in A. That expectation was written down before any approach had been run on B.

6. Limits

  • One build and one run per approach. Each KB comes from a single order of A, and each approach was run once on B. The baseline suggests repeats add little, since few tasks change outcome between them, but the effect of the order in which A is seen is not measured.
  • A small benchmark. B has 41 tasks in 15 modules. The last line of this section gives the smallest difference it can tell from chance.
  • Thirteen approaches of 51. The rest are defined and can be run with the same command.
  • The KBs were built with the result shown. These results say nothing about a KB written by an agent that never learns whether it was right.
  • A public benchmark. The model may have seen these problems. That affects the baseline and every approach alike, but it narrows the room an approach has to help.
  • One agent and one model.
  • The network was open. The harness is built to confine the agent to the model's API, but that needs kernel support this machine's Docker lacks. Web search was off, the rules forbade network use, and every trajectory was read for it.
  • Three tasks are unusable. The reference for Prob013_least_common_multiple drives an output to high impedance, which its own testbench counts as a mismatch, so no answer can pass. The task checks found this.
  • One approach could not be run. Codex's own memory cannot be kept between runs under this executor, which recreates the CLI's home directory for every run.
  • Limitations are a model's reading. They describe; they are not scores.

Violations planted in certified baseline trajectories: the monitor flagged 20 of 20 (read grading assets 4/4, search for answers 4/4, fetch from network 4/4, fake the result 4/4, copy another runs answer 4/4). The judge flagged 20 and the pattern match 8.

Two repeats of the baseline differ by +0.0% (-7.1 to +7.0) on B. The smallest difference in pass rate this benchmark can tell from chance is about 9.5%.

7. Further work

  • Repeats and orders. Three chains per approach, each over a different order of A, would show how much a KB depends on what it happened to see first.
  • The remaining combinations, and one setting changed at a time on the approaches that did best: what the key describes, how entries are maintained, whether a use count is kept.
  • Hill climbing on A. Repeated passes over A that keep a change to a KB only if it helps, with B untouched until the end.
  • A root-cause measure, scoring whether the agent found the cause apart from whether it fixed it. It needs a recorded fault location per task to be worth having.
  • A harder benchmark. Only the adapter is specific to ChipBench.
