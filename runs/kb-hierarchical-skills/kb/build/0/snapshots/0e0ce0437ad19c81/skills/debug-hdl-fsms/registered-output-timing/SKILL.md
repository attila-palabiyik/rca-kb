# Registered output timing

- For a shift-register detector, trace one input sample through the actual register assignment. Verify that each retained bit moves one position toward the oldest end and that the new sample enters the newest end. For a nine-bit register with the oldest sample at bit 8, `{history[7:0], a}` shifts the history toward bit 8 and inserts `a` at bit 0. Then map the fixed pattern bits to the comparison slices and check their constants. Preserve the sampling edge when both predicates already read the intended window.
- Trace each predicate across a rising edge. A clocked comparison of a shift register reads its pre-edge value, while a combinational comparison of the same register sees the updated value after nonblocking assignments settle. Combining the two predicates can mix adjacent windows.
- Compare the existing output pipeline with the requested timing before editing. If the intended output is a registered comparison of the stored window, evaluate every predicate using that pre-edge window. Comparing against the next shift-register value instead advances detection by a cycle. Preserve reset initialization and add a sample-valid gate only when the required startup behavior calls for one.
- Verify timing with an isolated match. Check the output immediately after the final input bit is sampled and again after the following edge, allowing nonblocking assignments to settle. Test reset separately, including whether reset-filled history contributes to early windows. A testbench that assumes the proposed latency can pass every pattern and still miss the timing bug.

- In the shift-assignment variant of the graded `TopModule` detector for `011XXX110`, `{a, a_tem[7:0]}` overwrote bit 8 while bits `[7:0]` held their reset values. Changing the assignment to `{a_tem[7:0], a}` alone matched all 237 reference samples. The registered comparisons still read the pre-edge window, so `match` asserted one rising edge after the final bit was sampled.
- In the comparison-constant variant of the same detector, changing the registered prefix comparison on bits `[8:6]` from `001` to `011` matched all 237 reference samples. The shift register started with zero-filled history. A rewrite that compared the next window and added a nine-sample startup gate disagreed with the reference on 16 of 237 samples.

## Counter status flags

- If the specification places a status pulse in the cycle after a count is reached, register the comparison against the current count using the counter's clock edge. Trace both the edge that enters the count and the edge that leaves it. Check reset release between edges, especially when the reset count satisfies the comparison but the flag resets low.
- In the graded decimal up/down counter, the reference replaced the combinational zero decode with a rising-edge comparison of the stored count and an active-low asynchronous reset for the flag. The submitted fix put the counter and flag in the same clocked block and matched all 289 samples. Entering zero during counting left the flag low for that cycle. The next edge asserted it as the count moved away from zero. After reset release, the flag stayed low until the first rising edge, which sampled the reset count of zero.

## Fractional clock dividers

- For a repeating schedule of integer periods, divide each segment length by its selected period length. Each quotient should be integral when the selector changes at a period boundary. Sum the quotients to get the number of output cycles per block. Verify that the period counter wraps on the same edge that changes the selector.
- Reconcile any contradictory cycle-count example with the stated ratio and the configured schedule. Test the rising-edge intervals and the high-pulse widths across the mode switch and the schedule wrap. A zero-based counter comparison `count <= limit` includes `limit + 1` clocks. For a registered output, use the counter and selector values before the sampling edge.
- In the graded 8.7× `TopModule` divider, 24 input clocks at divide-by-8 and 63 at divide-by-9 yielded 10 output periods per 87 input clocks. The even-mode comparison used `div_e >> 3`, yielding three high clocks. Changing only that shift to `div_e >> 2` yielded four high clocks in both modes and matched all 2,021 reference samples. Icarus simulation also checked the repeating waveform and asynchronous reset during a high pulse.
- Compare pulse-width expressions at relevant parameter overrides before substituting them. For example, `count < (divisor >> 1)` agrees with `count <= ((divisor >> 2) + 1)` at divisors 8 and 9. At divisor 17 the former yields eight high clocks and the latter yields six.

## Arithmetic pipelines

- When an arithmetic result appears a cycle early, trace the final operation across a rising edge. A combinational sum of registered partial sums reflects the newly captured operands after the edge. A clocked sum with a nonblocking assignment uses the pre-edge partial sums and produces the result on the following edge. Add the output register only when that additional stage matches the required timing.
- Drive distinct products on consecutive rising edges and check the output after each edge settles. Pulse asynchronous reset entirely between edges while a product is in flight. Check for an immediate zero and verify that the first rising edge after release still outputs zero as it captures fresh operands.
- In the graded output-timing variant of the 4-bit unsigned `TopModule` multiplier, both partial sums already contained the correct terms. Registering their final sum with a rising-edge nonblocking assignment and active-low asynchronous reset matched all 43 reference samples. The first stage sampled the operands on one rising edge and the output register delivered their product on the next.

## Parallel operand paths

- At each clocked stage, trace the sampling edge of every operand. If an operand bypasses an earlier registered stage, register it in parallel with that stage using the same clock and reset. Use consecutive, distinct input samples that make a mixed-cycle result differ from the expected result.
- Preserve existing submodule port names during a timing fix. A testbench may instantiate the submodule directly with named ports. When checking interface compatibility locally, instantiate it with its original named connections and compile alongside a test of the top-level timing.
- In the graded three-input unsigned minimum `TopModule`, the second comparator consumed the registered minimum of `a` and `b` alongside live `c`. The supplied correction only changed `c1` into a rising-edge register with an asynchronous active-low reset, matching the first comparator's timing. The submitted fix also renamed the comparator inputs from `a` and `b` to `data_a` and `data_b`. Its top-level Icarus simulation passed, but grading reported a testbench compile failure. The supplied correction retained the original port names.

## Stream width converters

- Compare the counter's advance condition with the input capture enable. For a ready/valid input, a transfer requires `ready && valid`, so the counter holds when `!ready || !valid`. Check both one-high cases. Even an interface described as always ready can use a registered ready signal that is low during reset and through the first sampling edge after release. Drive valid across that edge and use the pre-edge ready value when checking acceptance.
- When repairing a specific bug in supplied RTL, distinguish the input transfer condition from the existing output data and valid timing. If those outputs use different predicates, trace both independently. If the prose and RTL imply different behavior, isolate the demonstrated defect and use directed tests to expose any additional observable changes before adopting them.
- If `valid_out` marks a newly completed registered word, check that it uses the same sampling edge and load condition as `data_out`. A combinational decode can assert while `data_out` still holds the previous word and drop when the counter advances on the completion edge. Register the load predicate when this is the mismatch. When the current input supplies the final bits, the load predicate requires both the completion position and input acceptance. Check an idle cycle at the completion position and sample both outputs after the edge that accepts the final bits and after the next edge.
- Two graded serial-to-6-bit `TopModule` variants required different counter fixes. In the hold-condition variant, the reference changed `~ready_a && ~valid_a` to `~ready_a || ~valid_a` so the counter and shift register advance on the same transfers. In the wrap-comparison variant, the hold condition was already correct. The reference changed only the wrap comparison from `cnt == 4` to `cnt == 5`. The old comparison returned to zero on the fifth accepted bit, so neither output could see a pre-edge count of 5.
- Both references retained registered `ready_a`, which resets low, and `valid_b <= cnt == 5` outside reset. In the wrap-comparison variant, the first rising edge after reset release raises ready. Input acceptance can begin on the following rising edge. An idle edge at count 5 asserts `valid_b` while `data_b` holds its prior value. The submission repaired the wrap but also tied `ready_a` high and gated `valid_b` with input validity. Its local Icarus tests covered all 64 words, gaps, consecutive groups, and reset under the rewritten timing. Grading still reported 16 mismatches out of 151 samples, with no breakdown by change. Include both the first edge after reset release and an idle edge after the fifth accepted bit in compatibility tests before changing either output.
- When input beats can straddle output word boundaries, derive each completion from the cumulative bit count and check the full repeating pattern. For a counter that starts at zero and advances only on accepted inputs, output word `k` (starting at 1) completes on the edge with pre-edge count `floor((k * output_width - 1) / input_width)` within a packing period. Compare each count with both the data load and the valid decode. An independent testbench can append accepted bits in stream order and check both outputs whenever it collects a complete word.
- In the graded 24-to-128-bit `TopModule`, 16 accepted inputs formed three words. The data register loaded at pre-edge counts 5, 10, and 15 using 8, 16, and 24 bits from the current input, respectively. In the comparison-constant variant, changing `cnt==12` to `cnt==10` in the valid decode matched all 261 reference samples. In an earlier variant, correcting the input-valid gate from OR to AND also matched all 261 reference samples. Both fixes used the existing data slices, which already carried unused bits into the next word.
- In the output-timing variant of the 24-to-128-bit `TopModule`, the completion counts and `valid_in` gate already matched the data load condition. Registering that predicate at the rising edge with the existing active-low asynchronous reset was the only functional change and matched all 261 reference samples.
- If output valid already aligns with word completion but the stored portion of the word is wrong, trace the staging register's write enable and its value just before the completion edge. Check with distinct accepted values and with changing bus data during invalid cycles. Avoid changing output latency when the error is in input capture.
- In the graded 8-to-16-bit `TopModule`, the staging register originally loaded on invalid cycles and held on valid cycles. The reference reversed the mux branches so that it captured every valid byte and held through gaps. The submitted fix captured only the first valid byte of each pair and matched all 141 samples. On the edge that accepts the second byte, the output register reads the pre-edge staging value, so a simultaneous nonblocking update to the staging register cannot change the completed word. The next pair captures its own first byte before the staging value is read again.
