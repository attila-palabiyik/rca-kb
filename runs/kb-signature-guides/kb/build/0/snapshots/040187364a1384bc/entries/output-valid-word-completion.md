# Output valid and word completion

Applies when a word packer or similar accumulator asserts output valid before the edge that writes the word, misses a completed word, or reasserts valid during idle cycles at a completion boundary.

If the word boundary itself moves during an input stall, compare the counter enable with the input capture enable first. The [ready/valid word counter guide](ready-valid-word-counters.md) covers a case where fixing the count was sufficient for the reference, which retained different enables for output valid and output data.

1. Find the clock-edge condition that writes the output data. Trace the counter just before that edge and identify whether it counts accepted inputs or elapsed clocks. With nonblocking assignments, a counter that has already counted five inputs still reads as five on the edge that accepts the sixth.
2. Compare the data-write and valid conditions on the same edge. Check both the input acceptance gate and each completion count. If the counts differ, drive an accepted input at each differing count and check for a missing pulse where data is written and a spurious pulse where data is held. Pause immediately before a completion beat to check that neither event occurs during the stall. An OR between acceptance and completion lets valid assert on both partial inputs and stalls at completion. When the interface marks each newly written word with a pulse, use the same acceptance-and-completion condition for that pulse and the data write.
3. If the conditions match, check how each is sampled. With a combinational valid decode, an update to the counter or `valid_in` can raise valid while the output register still holds the previous word. On the completion edge, the counter can advance and drop valid just as the new word appears. Keep `valid_in` high through a completion and check both outputs before and after the rising edge. If the interface requires valid and data to appear together after the edge, register valid using the same pre-edge condition as the data write. Check that valid clears on the following edge and on asynchronous reset.
4. Check packing independently before changing counter thresholds or slices. For `TopModule.sv`, the 24-to-128-bit packer completed words on accepted inputs 6, 11, and 16 of each 16-input group. Those words used 8, 16, and 24 high bits of the incoming beat, respectively. A bit-stream scoreboard checked bit order and carryover across those boundaries, with gaps immediately before completion and an asynchronous reset while output valid was high.

- In the `TopModule.sv` 24-to-128-bit converter with premature and idle-cycle output valid, changing OR to AND in the registered `valid_out` condition passed all 261 grading samples.
- In the `TopModule.sv` 24-to-128-bit converter with a missing pulse and a later spurious pulse, the acceptance gate was already correct. The data write used counts 5, 10, and 15, while `valid_out` used 5, 12, and 15. The 11th accepted input wrote the second word without a pulse, and the 13th raised a pulse while holding that word. A local bit-stream scoreboard confirmed the packing, so only the middle valid count changed from 12 to 10. The one-line fix matched all 261 grading samples.
- In the `TopModule.sv` 24-to-128-bit converter with combinational `valid_out`, both conditions already used `valid_in` and counts 5, 10, and 15. For example, with continuous input, valid rose after the fifth input advanced the counter to 5 and fell after the sixth input wrote the first word and advanced the counter to 6. Registering the existing decode with an active-low asynchronous reset matched all 261 grading samples. The counter and packing logic required no edits.
