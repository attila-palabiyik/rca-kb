# FIFO pointer updates that miss the RAM clock edge

Applies to a synchronous FIFO when asserting a request changes a pointer or status flag between clock edges, a single write appears to advance the pointer repeatedly, or the first word is read back from the wrong slot.

1. Start from reset with the FIFO empty. Drive the first write request away from the rising edge and trace the write pointer, RAM write enable, and RAM write address. The pointer should hold until the rising edge. At that edge the RAM uses the current pointer, and the pointer advances by one slot after the edge. A flag derived from the pointers should reflect the new occupancy after the pointer updates settle.
2. Compare the read and write pointer blocks with the RAM sampling edges. In this task, the read pointer already used a rising-edge block with an active-low asynchronous reset. The write pointer used `always @(*)` and assigned a value computed from itself. Holding the pointer with a self-assignment when disabled did not make it edge-triggered. The reference put the write pointer in a `posedge clk or negedge rst_n` block and used nonblocking assignments, mirroring the read pointer.
3. Verify the first write and read, then fill and drain across a wrap and exercise simultaneous requests. Check both the accepted transfers and the flags. The original wrap logic, occupancy arithmetic, and RAM wiring were all present in the reference fix, so changing them was unnecessary to correct this failure. Check boundary behavior against the interface before changing request gating. This FIFO accepted only the read when both requests arrived at full and only the write when both arrived at empty.

Source task was `TopModule.sv`, a parameterized synchronous FIFO using a supplied dual-port RAM. The submitted fix also replaced the occupancy arithmetic with direct address and wrap-bit comparisons and gated the RAM enables during reset. It passed all 327 grading samples. The supplied reference fixed the write pointer block alone, establishing that the extra changes were unnecessary for the reported bug.
