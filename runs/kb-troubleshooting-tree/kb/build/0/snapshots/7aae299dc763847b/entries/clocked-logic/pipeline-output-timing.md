# Check the edge that publishes a pipelined result

**Check** the result just after the edge that captures a new input sample and just after the following edge. Drive successive samples with different expected results so an early or late output is visible. A combinational output follows the newly updated stage registers after the edge. A clocked output with a nonblocking assignment uses the values those registers held before the edge.

- **The result appears one edge early and the design calls for a registered final stage.** Register the final expression using the specified clock and reset. For a periodic output, check both the first update after reset and the spacing of later updates. Check that asynchronous reset clears the output and any in-flight results.
- **The data and its status flag report different cycles.** Trace both outputs to the state they sample. On an edge that captures a visibly different value, such as loading a nonzero count from zero, compare the data and flag both after that edge and after the next. If the flag already samples the pre-edge state and the data should be published one edge after capture, register the data from that same state and preserve the flag's reset value. If the data is supposed to publish on the capture edge, follow the [output flag timing check](output-flag-timing.md).
- **The result appears one edge late and the design calls for a combinational final stage.** Check for an extra output register.
- **The result appears on the intended edge.** Inspect the arithmetic and reset behavior if the output still fails.

**Observed in `TopModule.sv`**, an unsigned 4-bit pipelined multiplier with a combinational final sum after the registered partial sums. The reference fix registered the final sum on `posedge clk` and cleared it on `negedge rst_n`. The product appeared on the rising edge after its partial sums were captured. The submitted fix made the same change and matched all 43 graded samples.

**Observed in `TopModule.sv`**, a hexadecimal settable counter with a combinational count output and a registered `zero` flag. The reference registered `number` from the internal counter `num` and kept the existing flag logic. Both outputs sampled the pre-edge value of `num`, so a `set` value appeared at `number` one rising edge after capture. For example, when loading `7` from an internal count of `0`, the outputs immediately after the load edge were `number = 0` and `zero = 1`. After the following edge they were `number = 7` and `zero = 0`. During asynchronous reset both outputs were `0`. The submitted fix published the new count and its zero comparison together on the capture edge and asserted `zero` during reset. Its simulation verified those assumptions, and grading found 248 mismatches in 273 samples. When the prose leaves the capture-to-output latency ambiguous, check what each existing output samples before deciding which path to change.

**Observed in `TopModule.sv`**, a 4-bit Gray counter specified to advance every two rising edges. The reference kept the existing Gray-to-binary and increment stages and registered `gray_out` from the internal Gray wire with an asynchronous active-low reset. The output sampled the pre-edge Gray wire, so it stayed at `0000` on the first rising edge after reset release and published `0001` on the second. The submitted fix changed the decoder to nonblocking assignments and kept the output combinational. Its simulation passed a sequence check that assumed the first update was on edge one, but grading found 202 mismatches in 421 samples. Check the expected output on each of the first two rising edges after reset release before using a steady-state cadence check to validate a fix.
