# Check reset behavior when decoding FSM outputs

**Check** whether moving a registered output to a combinational state decoder changes when the output clears on reset. Trace reset assertion while the current state still selects an asserted output, before and after the state register's nonblocking update. Also check which signal changes first trigger the decoder at startup.

- **The output must clear in response to reset itself.** Give active reset priority in the combinational decoder and include reset in its sensitivity, for example by reading it in `always @(*)`. Test assertion with the clock stopped while each result output is high. A check after the simulation time slot settles can pass with either implementation, so inspect the event ordering when reset timing matters.
- **The reset state is sufficient for the required timing.** Check when the decoder first runs and whether it assigns every output on all paths. Then verify the transition into the result state and the following clock edge.

**Observed in `TopModule.sv`**, a Moore FSM that checks `011100` in non-overlapping six-bit groups. The original clocked outputs read the pre-edge state, reporting the result one edge after the FSM reached its result state. The attempted fix decoded the current state with `always @(*)` and relied on the asynchronously reset state to clear the outputs. It passed local checks of all 4,096 ordered pairs of groups and settled reset behavior, but differed from the reference on 1 of 1,215 samples. The supplied correct fix gave active-low reset priority in the decoder and used an explicit sensitivity list containing `pstate`, `data`, and `rst_n`. The failing sample was unavailable, so the grading does not establish whether reset ordering or a difference in when the decoder ran caused the mismatch.
