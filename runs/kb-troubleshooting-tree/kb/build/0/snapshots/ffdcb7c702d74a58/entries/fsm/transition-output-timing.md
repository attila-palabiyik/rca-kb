# Check how a state transition reaches registered outputs

**Check** which edge updates each register between a next-state decision and the observable outputs. Compare the output just after the edge that enters the result state with the output just after the following edge. For each edge, use the values present before the edge to evaluate the nonblocking assignments. Include any counter reload condition that reads those registers.

- **The output asserts on entry to the result state, and the specification calls for the following cycle.** Register the decode of the current state on the FSM clock and give reset priority. For a result state that lasts one cycle, check that the flag is low at entry, high at the following edge, and low one edge later. Check that asserting reset clears the flag and cancels any pending pulse.
- **The timing already matches the specification.** Keep the existing trigger and register stages when correcting a next-state destination. If there is a counter, check the last count in the old state and the first count in the new state.
- **The outputs and counter reload land on different edges.** If the reload compares a visible light with its buffered value, go to [the phase-entry reload check](phase-entry-reload.md). If the discrepancy occurs during reset or startup, go to [the output decode and reset check](output-decode-reset.md).

**Observed in `TopModule.sv`**, an overlapping `1011` detector with a flag timing bug. The original combinational decode asserted `flag` as soon as the edge sampling the final `1` entered `S4`. The submitted and reference fixes both registered `state == S4` with asynchronous active-low reset, so the flag asserted on the next rising edge. Both used the original transition table, which already retained the `10` suffix on `S3` with input `0`. The submission matched all 153 grading samples. For `10110111`, matches complete at samples 4 and 7, so the flag should pulse at samples 5 and 8. The same pattern in an earlier task had a different fault. See [the suffix fallback check](sequence-suffix-fallback.md).

**Observed in `TopModule.sv`**, a traffic-light FSM with incorrect red and green destinations. The grading reference changed red to advance to green and green to advance to yellow. It kept the comparison at 3 and retained both output register stages and the original reset behavior. On an ordinary countdown, the edge sampling 3 updates the FSM state and produces count 2. The next edge updates the buffered lights and produces count 1. The following edge sees the difference between the buffered and visible lights, updates the visible lights, and reloads the timer on that same edge. The original comment predicted a visible count of 0, which the reload logic skips on this path.

The submitted rewrite changed the destinations, removed the register stages, and drove red during reset. Its local tests passed against that interpretation of the prose, but 220 of 517 graded samples differed from the reference. The grade gives an aggregate for the rewrite, so it does not isolate the failures attributable to reset or any other individual change.
